## Context

角色的特性統一由 `CharacterFeature` 表達，四個欄位：

```dart
CharacterFeature({ name, nameEn, source, description })
```

建角時（`character_create_page.dart:366-371`）由三個來源攤平而成：

```dart
final features = <CharacterFeature>[
  ...classFeatures,                                     // 內容庫，三欄俱全
  for (final t in sp.traits)
    CharacterFeature(name: t, source: '種族：${sp.cn}'),  // 整串塞進 name，description 空
  CharacterFeature(name: bg.originFeat, source: '背景：${bg.cn}'),
];
```

種族特性的來源 `SpeciesOption.traits` 是 `List<String>`，內容長這樣：

```dart
traits: ['矮人韌性 毒抗', '矮人堅毅 +1HP/級', '石工直覺 震顫感知', '黑暗視覺 120'],
```

顯示端（`biography_tab.dart`）已經備好三層結構：粗體 `name` ＋ 灰色 `nameEn`，接著 `if (features[i].description.isNotEmpty)` 才印說明。職業特性走得到那個分支，種族特性走不到。

另有第二個顯示點：建角種族步驟的敘述卡（`character_create_page.dart:616`）直接把 `_species!.traits` 攤成文字列。

## Goals / Non-Goals

**Goals:**

- 種族特性有名稱與說明兩件事，且分別存放——資料形狀對得起顯示端早就準備好的結構
- 玩家在建角當下與角色頁都能點開特性看懂它在做什麼
- 同一份特性清單只有一種互動，使用者不必自己學哪些能點
- 既有角色不因此壞掉

**Non-Goals:**

- **特性的機制自動化**：說明仍是純文字，不做規則引擎
- **接內容庫的 `races` 表**：見 D2，本版說明採手寫
- **既有角色的特性回填**：見 D4
- **背景起源專長的結構化**：`originFeat` 仍是字串，屬於專長系統的範疇（見 `custom-species` design D7 對專長現況的分析）
- **自訂種族**：歸 `custom-species`；本 change 只動內建種族與呈現

## Decisions

### D1：`SpeciesTrait` 三欄，映射直接對齊 `CharacterFeature`

```dart
class SpeciesTrait {
  final String name;         // '矮人堅毅'
  final String nameEn;       // 'Dwarven Toughness'（選填）
  final String description;  // '每個等級的生命值上限 +1。'
}
```

建角送出時 `SpeciesTrait` → `CharacterFeature` 是欄位對欄位的映射，`source` 由建角流程填入。**不需要改動 `CharacterFeature`**——它的形狀本來就是對的，問題只在餵進去的資料被預先黏成了字串。

- 為什麼不是「把現有字串在顯示時切一刀」：現有字串切第一個空格會得到「矮人堅毅」+「+1HP/級」，後者是縮寫不是說明。切法也不穩定（「黑暗視覺 120」切完是「黑暗視覺」+「120」）。要有真正的說明就得寫，寫了就該存成獨立欄位。

### D1a：黑暗視覺由距離推導，消掉重複的表示法

`SpeciesOption.darkvision`（bool）改為 `darkvisionFt`（int，0／60／120），黑暗視覺的特性條目由它推導（`allTraits`），各種族的 `traits` 不再各寫一遍。

拆特性時才發現同一件事有兩種表示法並存：

- `darkvision` bool **全 App 只用在建角敘述卡的一個 chip**，沒有寫進角色卡、無任何機制用途
- 5 個種族的 `traits` 又各自寫了「黑暗視覺」或「黑暗視覺 120」

結果建角選矮人時，卡片上同時出現沒有說明的「黑暗視覺」chip 與帶說明的「黑暗視覺 120」特性。而且 **bool 表達不了距離**（60 與 120 差一倍），**精靈甚至漏了那條 trait**（SRD 2024 精靈有 60 呎黑暗視覺）。

- **為什麼是推導而不是刪掉其中一邊**：刪 chip 只是把重複藏起來，兩種表示法還在；刪 traits 則失去距離與說明。改成單一數值欄位＋推導，距離保住、說明統一生成、資料只有一個來源。
- **對 `custom-species` 的影響**：編輯頁的「黑暗視覺」由開關改為 0／60／120 選單，使用者不必自己打字寫特性，也不會寫出與距離矛盾的說明。

### D2：內建說明手寫，不接內容庫

內建 9 個種族的特性中文說明由本 change 手寫補齊（去除重複的黑暗視覺後共 27 條，另加由距離推導的黑暗視覺）。

- **替代方案：接 `races` 表。** 內容庫已匯入 SRD 原文（`entries` 欄位），且在 CC-BY 授權範圍內。但那張表目前**全 App 無人消費**（與 `feats` 表同樣狀況），接它要處理查詢、快取、5etools 標記渲染、離線降級——是獨立的一塊工，混進來會讓這個本來很小的 change 失控。
- 手寫版定位是「點開看得懂這個特性在做什麼」，不是規則原文全文。日後接內容庫時**結構已經到位**，可整批替換說明內容而不動形狀。
- 這也保留了自訂種族的對稱性：自訂種族沒有內容庫可查，說明本來就得由使用者自己寫。

### D3：兩處清單統一為點擊展開

建角種族步驟的敘述卡與角色頁的特性清單，皆為「清單只顯示名稱，點擊出說明」。角色頁的職業特性一併改。

- **為什麼連職業特性一起改**：同一份清單裡混用「有些可點、有些直接展開」，使用者得自己學規則。一致性的價值高於「職業特性少一次點擊」。
- **附帶好處**：職業特性隨等級累積，說明常駐會讓傳記頁越拉越長；改為收合後清單可掃視。
- 呈現沿用 App 既有的說明彈窗慣例（決策頁的狀態異常 chip 已是點擊出說明）。
- **建角步驟本來就該收合**：種族敘述卡空間小，四條特性的說明攤開會把選擇流程推很下面。

### D4：無說明不給點擊——降級是規則的自然結果

`description` 為空時，該列 SHALL NOT 呈現可點擊的視覺提示。

這條規則同時解決三件事：

1. 避免留下按了沒反應的觸控目標
2. 既有角色的特性快照（整串在 `name`、說明為空）自動退化成現況的單行呈現，**不需要任何相容分支或回填**
3. 背景的起源專長（仍是字串、無說明）同樣自然降級

使用者已確認既有角色皆為測試資料，只要畫面不壞即可。若日後要回填，可依種族名比對新的結構化清單重建，與本 change 的設計無衝突。

## Risks / Trade-offs

- **職業特性的說明多一次點擊**：原本掃一眼就看得到。→ 換來清單可掃視與互動一致；高等級角色的特性數量會讓常駐說明變成負擔。

- **手寫說明的品質不如 SRD 原文**：必然較簡略。→ 定位是「看得懂在做什麼」；結構到位後日後可整批替換（D2）。

- **改動觸及內建常數與既有畫面**：`SpeciesOption.traits` 換型別會動到 9 個種族的定義，互動改動影響傳記頁。→ 範圍雖廣但性質單純（形狀轉換＋呈現），機制欄位完全不動；以 widget 測試覆蓋新舊兩種資料的呈現。

- **新舊角色的特性呈現不一致**：新角色的種族特性可點開看說明，舊角色的不行。→ 既有角色為測試資料，可接受；規則本身（無說明不給點擊）讓這個差異不會表現為錯誤，只是舊角色少了說明。

## Migration Plan

**無 migration**。不涉及資料表；角色的特性快照欄位形狀不變。

**既有資料**：不處理，靠 D4 的規則自然降級。

**Rollback**：回退版本即可。已用新版建立的角色，其特性快照含 `description`——回到舊版後那些說明不會顯示（舊版的種族特性顯示路徑不讀 `description`），但不會出錯。

## Open Questions

1. 說明的呈現用彈窗（Dialog）還是底部 sheet？決策頁的狀態異常目前用彈窗，傾向一致。
2. 特性列要用什麼視覺提示表示「可點開」？傾向與 App 既有的可展開元件一致，避免新增語彙。
3. 內建說明的用字長度上限？傾向每條 1–2 句、控制在 60 字內，讓彈窗不需捲動。
