## Context

> 本檔與 proposal 一樣是**事後補寫**（2026-09-22）。以下決定都能在程式碼裡
> 指認出來，但當時沒有寫下理由——D3、D4、D7 三項尤其容易在半年後被當成
> 「隨手寫的」而改掉。

角色卡的法術由 `Spell`（`next/lib/domain/character.ts:55`，zod schema）描述，分成兩個陣列：`cantrips`（戲法）與 `spells`（環級法術）。這個型別已經有自創法術需要的大部分欄位：

| 欄位 | 用途 |
|---|---|
| `name` / `nameEn` / `level` | 識別與分組（`RING_LEVELS` 依 `level` 分環顯示） |
| `description` / `upgrade` | 顯示文字 |
| `damage` / `damageType` / `range` | 顯示用，不驅動骰子計算 |
| `castingTime` | 純顯示字串（如 `'1 動作'`） |
| `castKind` | **邏輯判斷看這個**（`action` / `bonus` / `reaction` / `other`），行動頁依此分組 |
| `prepared` | 已備法術旗標 |
| `concentration` | 專注——`Character.concentrationSpell` 與之連動 |

SRD 法術則來自內容庫的 `v_spells`（匿名可讀、唯讀），型別是 `CatalogSpell`，與 `Spell` 是不同的東西：前者是內容庫的一列，後者是角色卡裡的一筆快照。建角時選 SRD 法術，就是把 `CatalogSpell` 轉成 `Spell` 寫進角色。

前三個型別（背景／種族／子職）已建立完整的 homebrew 模式，本 change 沿用整套：文件模式表、zod schema、server actions、管理元件（`embedded` 模式）、`/library` 區塊化呈現、`HOMEBREW_KIND` 註冊表。

## Goals / Non-Goals

**Goals:**

- 玩家能撰寫 SRD 沒收錄的法術，並在角色的法術頁看到它——含施法時間、專注、升環等會影響跑團操作的欄位
- 選用即快照：之後編輯或刪除收藏不影響已選用的角色
- 自創法術**不得污染官方規則推導**——同名不同物，不能讓自創法術觸發內建的機制判斷
- 沿用註冊表，讓分享／檢視／收藏三條路徑自動支援

**Non-Goals:**

- **法術位與施法資格的自動化**：見 D6。選用自創法術不增減法術位，也不檢查「你這個職業這個等級能不能用」
- **傷害骰的自動擲骰或結算**：`damage` 是顯示字串，與 SRD 法術一致
- **修改或覆寫 SRD 法術**：內容庫唯讀
- **法術清單的自訂排序／標籤**：沿用既有的依環數分組
- **建角流程整合**：見 D4
- **法術的規則版本標記**：歸 `dual-rules-version`

## Decisions

### D1：`CustomSpell` 以角色卡的 `Spell` 為基底 `extend`，不另立型別

```ts
export const CustomSpell = Spell.extend({ id, name, level, description, ... });
```

三個理由：

1. **快照轉換不會漏欄位**。`spellFromCustom()` 只需處理「要合併進 description 的那幾個顯示欄位」，其餘直接帶過去。若兩邊是獨立型別，每次 `Spell` 加欄位就要記得同步——而忘記的徵兆是「自創法術少了某個行為」，不會有型別錯誤。
2. **`castKind`、`concentration`、`prepared` 這些驅動邏輯的欄位語意完全相同**。自創法術的專注與 SRD 法術的專注是同一件事，`Character.concentrationSpell` 不該分辨來源。
3. `Spell.parse(spellFromCustom(s))` 因此恆成立，且測得到（見 tasks 5.2）。

`extend` 而非 `Spell` 直接加欄位：`id`、`school`、`duration`、`components`、`ritual` 只有「收藏裡的那一份」需要，角色卡的快照不需要——它們在快照時已經併進 `description` 的首行。

### D2：選用即快照，`homebrewId` 只作標記不作回查

`addCustomSpell()` 把 `spellFromCustom(s)` 的結果寫進角色的 `cantrips`／`spells`，並帶上 `homebrewId = s.id`。

`homebrewId` **不是外鍵**，任何讀取路徑都不會拿它回查 `user_spells`：

- 與整個 App 的快照哲學一致（角色卡是自己那一份，來源刪改不影響）
- 分享檢視端讀不到擁有者的 `user_spells`，若要回查就會兩端顯示不同
- 跑團當下的法術頁不能為了顯示一道法術多打一趟往返

它的用途是三件事：**去重**（同一道法術不重複選用）、**移除**（`removeCustomSpell` 以 id 找）、**規則隔離**（見 D5）。

「再次選用同一道法術」刻意**不覆寫**角色版本（`addCustomSpell` 直接回傳原角色）：那會讓「收藏改了」悄悄改掉角色的法術，與快照語意相反。要拿新版就先移除再選用——UI 上以「移除只影響角色，不會刪除收藏。重新選用會取得收藏中的最新版本」明示這條路。

### D3：法術頁的顯示條件放寬到「可編輯即顯示」

原條件是 `spellSlots.length > 0 || cantrips.length > 0`——沒有法術位也沒有戲法的角色（戰士、野蠻人、盜賊）看不到法術頁。這是對的：空的法術頁沒有意義。

但自創法術把這個前提打破了：**DM 給戰士一道戰役專屬的法術**是合理的桌上情境，而按原條件那道法術選進去之後，角色卡上根本沒有地方顯示它。

因此條件改為 `... || c.spells.length > 0 || !!spellTools`：

- `c.spells.length > 0`——已經有法術就一定要能看到，不論怎麼來的
- `!!spellTools`——**可編輯的角色卡一律顯示法術頁**，否則戰士要選第一道自創法術時，入口本身不存在（雞生蛋問題）

代價是明確的：戰士的角色卡從此多一個法術頁，裡面只有施法卡與「從收藏選用法術」。這是刻意的取捨——多一個大致為空的分頁，比「有法術卻無處顯示」好。`spellTools` 只在 `persist` 時傳入，所以**唯讀的分享檢視不受影響**：分享出去的戰士角色卡沒有法術頁，除非他真的有法術。

### D4：建角流程不提供自創法術

`create-wizard` 的法術步驟只給 SRD 法術（依職業與環數過濾），不合併自創法術。理由是**消費點不同**：

- 背景／種族／子職是「建角時選一個，之後不再改」——自然的整合點就是建角流程，不在那裡給就沒有別的地方給
- 法術是「隨時往角色裡加很多個」——建角時選的那幾道戲法與一環法術受職業額度限制（`cls.cantripsKnown`／`cls.preparedSpells`），而自創法術**不佔額度**（見 D6）。把不佔額度的東西混進「已選 2/3」的計數器裡，那個分數就說不清是什麼

因此自創法術一律在角色卡的法術頁選用，建角完成後隨時可加。這與 `custom-species` design Open Q4 的結論同向：**自創內容的編輯與選用入口集中在收藏紀錄與角色卡，不在建角流程裡就地長出來。**

副作用是建角當下無法帶入自創法術，要多走一步（建完 → 法術頁 → 從收藏選用）。可接受：自創法術通常是跑團中途才出現的東西，不是建角時的必要決定。

### D5：`homebrewId` 作為規則隔離的判準

`lib/rules/ac.ts` 的 `knowsMageArmor` 原本是：

```ts
c.spells.some((s) => s.nameEn === 'Mage Armor')
```

自創法術的 `nameEn` 是使用者自由填寫的。玩家寫一道改寫版的「法師護甲」並沿用英文名，AC 公式就會套用官方法師護甲（13 + DEX）——**而他的自創版本可能根本不是那個效果**。徵兆會是「AC 莫名多了幾點」，且極難追。

修法是加上 `!s.homebrewId`：

```ts
c.spells.some((s) => !s.homebrewId && s.nameEn === 'Mage Armor')
```

這確立了一條通則：**任何以法術名比對來驅動規則推導的地方，都必須排除自創法術。** 自創法術是顯示內容，不是規則識別碼；同名只代表使用者選了同一個字串。目前只有這一處這樣比對，新增同類判斷時要記得一起帶上（本 change 沒有加 lint 規則擋——只有一處，加規則的成本高於收益，但這是個會隨處數增加而反轉的判斷）。

### D6：機制不自動化——不佔法術位、不檢查資格

選用自創法術：

- **不增減 `spellSlots`**：法術位由職業與等級推導（`lib/rules/` 的既有邏輯），自創法術不是職業能力，沒有理由改動它。要多一個法術位是 DM 的裁決，玩家自己在法術位上調
- **不檢查施法資格**：不問「你這個職業能不能學這道法術」「你的等級夠不夠這個環數」。SRD 法術有 `classes` 欄位可以過濾，自創法術沒有——而要使用者填「哪些職業可用」，等於要他先替一道自己發明的法術設計職業清單
- **`description` 與 `upgrade` 是顯示文字**，不做規則引擎（與 SRD 法術一致）

取代自動化的是**明示**：選用對話框寫「選用後立即保存角色副本，不會增加法術位。請與 DM 確認環數與使用資格」，管理區塊寫「採用前請與 DM 確認」。與自訂種族、自訂子職一致——**強度與資格是 DM 的職責，App 不替桌上的人做裁決。**

### D7：id 一律用 `randomId()`（2026-09-22 修正）

> **本節原本寫錯了。** 初版聲稱「背景／種族／子職都用 `generateShareToken()`，
> 法術用 `crypto.randomUUID()` 是唯一的偏離」。實際盤查後是**三套**：

| 型別 | 原本的 id 來源 | 熵 / 長度 |
|---|---|---|
| 角色、背景、子職 | `newCharacterId()` → `randomId()`（`lib/creation/id.ts`） | 96-bit / 16 字元 |
| 種族 | `generateShareToken()`（`lib/share/token.ts`） | 128-bit / 22 字元 |
| 法術（初版） | `crypto.randomUUID()` | 122-bit / 36 字元 |
| **收藏來的副本（全型別）** | `randomId()`（`collect-actions.ts:50`） | 96-bit / 16 字元 |

三者在安全性上等價——都是密碼學隨機、都不可枚舉，沒有重蹈自訂背景時間戳 id
的問題。差別只有形狀。

**收斂目標是 `randomId()`**，理由是它已經是這件事的正解，不是三個選項裡挑一個：

1. 它的 doc comment 明寫「使用者自有資料的 id（角色、自訂背景、自訂子職…）」——
   就是為這個用途存在的
2. **收藏他人分享的法術一律走 `randomId()`**（`collect-actions.ts`）。手動建立
   用別的，同一張表裡就會有兩種形狀的 id，而那個差異不代表任何東西
3. `generateShareToken()` 是**分享 token** 的產生器——capability URL 的載體，
   128-bit 是因為它會出現在網址裡。拿它產資料 id 是借用，語意不對

法術已改為 `randomId()`（任務 7.5）。

**種族仍用 `generateShareToken()` 產 id，那是另一筆既有偏離**，不在本 change
的範圍內：功能無影響（id 只是隨機值），但它把分享 token 的產生器用在資料 id 上，
語意錯位。要改是一行，但那屬 `custom-species`；記在這裡是為了讓下一個人知道
「種族那樣寫不是慣例，別照抄」。

### D8：驗證只管結構，不管平衡

`CustomSpell` 的 zod schema 負責：必填（`name`、`description`、`castingTime`）、環數 0–9 的整數、各欄位長度上限（`description` 20000、`upgrade` 5000、其餘 80–500）。

**不驗證**：傷害是否過高、環數與效果是否相稱、專注與持續時間是否合理。與自訂種族、自訂子職一致（見 D6 的同一條理由）。

長度上限的用途不是規則而是**防呆與儲存成本**：`data jsonb` 整份存，沒有上限的話一篇小說就進資料庫了。20000 字對一道法術的說明綽綽有餘。

### D9：新表一開始就採 0007 之後的形狀

`user_spells` 直接採複合主鍵 `(user_id, id)` 與 `source_*` 三欄——這兩件事是 0007 為 `user_backgrounds`／`user_subclasses` 事後補的。`user_species`（0009）已經這樣做，本表沿用。

不重走一次「先做錯再修」的理由很單純：那兩支 migration 的內容已經在檔案裡，照著抄比自己想一遍更不容易錯。

## Risks / Trade-offs

- **戰士的角色卡多一個大致為空的法術頁**（D3）。緩解：唯讀檢視不受影響；分頁內至少有施法卡。若實測後判定干擾，退路是把條件改回原樣並在物品頁或總覽另給入口——但那會讓「自創法術」與「法術」分家，比現在差
- **同名自創法術觸發官方規則**（D5）。已修 `knowsMageArmor` 這一處；風險在於**未來新增的名稱比對忘記帶條件**。緩解目前只有這份文件與測試（tasks 5.5）
- **id 形式不一致**（D7）。功能無影響，但增加讀 code 的人的困惑成本
- **沒有資格判定**（D6）。玩家可以把 9 環法術選進 1 級角色。這是刻意的（DM 裁決），但也代表 App 幫不上「我這樣對不對」的忙。`homebrew-share` 階段 9 若實作會改善檢視端，自己選用這條路仍不擋
- **`description` 併入顯示欄位的做法會讓快照的 description 與收藏的 description 不同**（前者多了首行的學派／儀式／持續／成分）。編輯收藏再重新選用時，使用者看到的是「多了一行」而非「內容被改」——可接受，但若日後要做「角色版本 vs 收藏版本」的 diff，這一層合併會擋路

## Migration Plan

1. migration `20260910043545_custom_spells.sql`：建表 ＋ RLS ＋ `homebrew_shares` 的 `kind` check ＋ `get_shared_homebrew` 的法術分支
2. 以 `supabase db push` 套用（linked 專案即正式環境）
3. 部署（`npm run build` ＋ `npx wrangler deploy`）

**順序不可顛倒**：程式碼先上線而表還沒建，收藏紀錄頁的法術區塊會直接報錯——`fetchLibrary()` 會對不存在的表查詢。反之（表先建、程式碼未上）沒有影響，沒有人會去讀它。

無資料回填：`homebrewId` 是 optional，既有角色沒有這個欄位就是沒有自創法術，語意正確，不需要像 `speciesHpPerLevel` 那樣回填。

## Open Questions

- **自創法術要不要參與「已備法術」的計數？** 目前 `prepared` 預設 true 但不進任何額度計算。若日後做備法管理（換日重備），自創法術該佔額度嗎？傾向不佔（同 D6），但那時法術頁會同時顯示兩種語意的「已備」
- **要不要讓自創法術宣告適用職業？** 不做的理由見 D6。但若 `homebrew-share` 階段 9 實作資格判定，法術會是唯一無法判定的型別
- **`school`（學派）要不要收斂成選單？** 目前是自由文字。SRD 只有 8 個學派，開選單符合「欄位即軌道」的原則（`custom-species` D1）；但學派目前純顯示、不驅動任何推導，收斂的收益只有一致性。待有規則消費它時再處理
