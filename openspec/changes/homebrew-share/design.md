## Context

動機與範圍見 proposal。以下為決定設計的既有事實：

**`character_shares`（0005）已建立可直接沿用的前例**：token 為 128-bit 隨機（base64url 22 字元）主鍵；表對 `anon` / `authenticated` 完全不可讀；檢視者只呼叫 `SECURITY DEFINER` 的 `get_shared_character(token)`，該函式唯一參數為 token、不接受任何可影響查詢範圍的參數、不回傳 `owner_id` 或任何「這個 token 屬於誰」的資訊。狀態機為 `not_found` / `revoked` / `deleted` / `ok`。**分享的角色卡讀的是活資料**，不是發布時的快照。

**現有使用者資料表的主鍵形狀不一致**，且成因與現況已查證：

| 表 | 主鍵 | 筆數 | 其中為時間戳 id |
|---|---|---|---|
| `user_characters` | `(user_id, id)` | 35 | 31 |
| `user_backgrounds` | `(id)` | 8 | **8** |
| `user_subclasses` | `(id)` | 0 | 0 |

`0002_user_characters_text_id.sql` 記錄了成因：角色 id 從 `uuid` 改為客戶端產生的 `text` 時，Flutter 端用 `DateTime.now().microsecondsSinceEpoch`——可枚舉且跨使用者可能撞號，故改為複合主鍵。**但這個修正沒有推及後來建立的 homebrew 表**（0004 / 0006 皆為 `id text primary key`）。

Next.js 端的 `newCharacterId()` 已改為 96-bit 隨機，但**既有的 8 筆自訂背景全部是 Flutter 時代的時間戳 id**——這不是假設性風險，是現況。

**既有 homebrew 型別**：`custom-backgrounds`（已完成，已移植 Next.js）、`custom-subclass`（已完成）。兩者共用的原則：驗證只管結構不管平衡；自訂內容為**顯示文字**不做機制自動化；選用時**快照**進角色卡。

## Goals / Non-Goals

**Goals:**
- 玩家能把自訂內容傳給 DM 審核、傳給團員採用
- 作者依審核意見調整後，已發出的連結／QR 自動反映，不必重發
- 收藏者取得的是一份屬於自己的副本，來源之後如何變動都不影響它
- 一套檢視／收藏機制涵蓋所有 homebrew 型別，新增型別不需重做流程
- 收藏不受角色狀態牽制，但在角色上使用時仍受規則約束

**Non-Goals:**
- 自訂職業／武器／法術的分享、公開索引、副本與來源的同步、共同編輯（見 proposal）

## Decisions

### D1：分享連結指向活資料，不是發布時的快照

**推翻原提案的凍結快照設計。**

原設計的理由是防「作者偷改」：DM 審過 v1，作者事後改成 v2，DM 不知情。但這個顧慮被 D2 的收藏快照擋掉了——**暴露窗口只存在於「看到」到「收藏」之間**，一旦收藏就免疫。而 DM 若要留存審核紀錄，收一份即可，**資料庫本身就是「我核准過的版本」的存證**。這比做一套版本簽核機制簡單太多。

凍結快照的代價則是實際會發生的：DM 要求調平衡 → 作者改 → 得重發連結 → Discord 裡已經貼出去的舊連結與已印出的 QR 全部指向舊版本。桌上跑團的調整是常態而非例外，每次調整都要重發是設計缺陷。

另有一致性的理由：`character_shares` 已經是活資料。兩套分享用兩種語意，使用者無從預期哪個是哪個。

**代價**：作者刪除來源後連結會失效。但這在 `get_shared_character` 已有現成處置（`deleted` 狀態），照抄即可，不是新問題。

### D2：收藏為快照複製，且刻意不做任何回連

收藏在收藏者自己的 `user_backgrounds` / `user_subclasses` 建立**新資料列**：新的隨機 id、自己的 `user_id`、內容取自按下當下的來源資料。

**新 id 是硬性要求**——那本來就是新的一份，而非同一份的第二個擁有者。此規則與 D3 的主鍵調整無關，兩者都要。

副本與來源之間**沒有任何同步機制**。要跟上來源就刪掉重收（D6 提供一鍵完成）。這不是偷懶：一旦允許同步，就得回答「使用者改過的欄位怎麼辦」「來源刪了副本怎麼辦」「已經拿去建角的角色要不要跟著變」——而快照哲學在角色卡那層已經給了答案，這裡沿用同一個答案，整類複雜度直接消失。

於是全鏈路是三層凍結：作者資料（活）→ 分享窗（活）→ 我的資料庫（凍結）→ 我的角色卡（凍結）。每一層都切斷上游變動，每一步的行為都可預測。

### D3：homebrew 兩表的主鍵對齊為 `(user_id, id)`

`user_backgrounds` 與 `user_subclasses` 由 `primary key (id)` 改為 `primary key (user_id, id)`，比照 `user_characters`。

**理由不是整齊，是現況有問題**：這兩張表的主鍵是全域的，而其中的 8 筆既有資料全部是 Flutter 產生的時間戳 id（見 Context）。這正是 `0002` 當初為角色修掉的狀態，只是沒有推及後建的表。跨使用者撞號的後果是 insert 直接失敗——第一個人測起來完全正常，問題只在第二個人身上出現。

本 change 正好放大這個風險：收藏功能會讓 homebrew 的 insert 量與跨使用者的 id 流動都增加。

**現在改幾乎沒有成本**（8 筆與 0 筆），日後改則要動使用中的資料與所有引用點。

**否決把 `user_characters` 改回全域主鍵**：複合是比較安全的那一形，角色已經有了，往回改是移除保護。

**後果**：`homebrew_shares` 需以 `(owner_id, homebrew_id)` 定位來源列——`owner_id` 本來就要存，這反而讓它與 `character_shares` 的 `(owner_id, character_id)` 對稱。

### D4：`homebrew_shares` 為指標表，比照 `character_shares` 的存取模型

表對 `anon` / `authenticated` 完全不可讀；檢視一律經 `public.get_shared_homebrew(p_token text)`（`SECURITY DEFINER`），回傳 `(status, kind, data, source_updated_at)`。

**不含 `rules_version`**：Next.js 端目前沒有任何 `rulesVersion` 欄位（`dual-rules-version` 凍結中），回傳一個恆為 `'5r'` 的欄位只是把推定值寫進 API 契約。待該欄位真正存在時再加。

RPC 的約束與 `get_shared_character` 相同：唯一參數為 token；不接受任何可影響查詢範圍的參數；不回傳 `owner_id`、`label` 或任何關於「這個 token 屬於誰」的資訊。狀態機沿用 `not_found` / `revoked` / `deleted` / `ok`。

`kind` 決定 RPC 內部去哪張來源表查（`background` → `user_backgrounds`，`subclass` → `user_subclasses`）。

> **更正既有文件**：`0006_user_subclasses.sql` 開頭與 `custom-subclass` design D3 都以「`shared_homebrew` 是**快照**表，所有型別在那裡只是不可變的 JSON，沒有各自的查詢需求」來論證 `kind` 欄位的正當性。改為活資料後這段論證不成立——`kind` 仍然需要，但理由變成「決定去哪張來源表查」。兩處註解需一併更正，否則後人會照著錯誤的前提推論。

### D5：兩段式行動——收藏無條件，套用受規則約束

檢視頁的行動區：

- **「收進我的資料庫」永遠可用**（僅要求登入）
- **「直接套用到這個角色」僅在規則允許時才渲染**

否決「單一使用按鈕依規則啟用／停用」：各型別的採用時機差異極大（背景與種族只在建角時、子職要 3 級且母職業相符、法術受職業與環數限制），統一在收藏時擋的結果是按鈕多數時候是灰的，而灰掉的原因對玩家不可見。

**規則過濾放在使用時而非收藏時**是關鍵取捨。一個法師子職躺在戰士玩家的資料庫裡不是錯誤狀態；他升戰士時它就是不出現，不需要錯誤訊息也不需要解釋。反過來若收藏時就擋（「你沒有法師角色，不能收」），既違反直覺，也讓「先收著以後建角用」——最自然的使用情境——變成不可能。

### D6：來源標記用旗標與時間戳，不用內容雜湊

收藏建立的資料列記 `source_token`、`source_updated_at` 與 `source_note`。`source_token` 為 null 即自己建立的。

由此可判斷兩件事：

| 判斷 | 依據 |
|---|---|
| 來源已更新 | 來源當下的 `updated_at` > 我的 `source_updated_at` |
| 我改過這份副本 | 我的 `updated_at` > 我的 `created_at` |

**「更新副本」是刪除＋重收的一鍵版本**，語意仍是快照。但若「我改過」為真，SHALL 先警告——否則一鍵更新會靜靜蓋掉使用者自己的修改，而那正是他刻意做的事。

否決內容雜湊：雜湊能精確判斷「內容是否相同」，但要為此定義穩定的正規化（欄位順序、空值、陣列排序），而 `updated_at` 已經夠用——誤判的方向是「明明沒變卻提示有更新」，成本只是一次多餘的提示。

**風險**：`updated_at > created_at` 依賴「只在使用者實際儲存時才 upsert」。若日後有無條件寫回的同步路徑（例如開啟編輯畫面就存一次），這個訊號會失準。manager 的儲存路徑需維持這個性質。

### D7：收藏來源的辨識靠收藏者自填的備註，不靠作者資訊

`get_shared_homebrew` 刻意不回傳 `owner_id`（沿用 `character_shares` 的隱私設計，D4），因此收藏來的項目只知道「來自分享」，不知道來自誰。

當下沒問題——使用者剛從某人的訊息點進來，他知道是誰。但三個月後打開資料庫看到五個收藏來的子職，記憶不會留著。而「這是 DM 核准的那一版」正是 D1 所依賴的存證用途，沒有標記就等於沒有存證。

解法是 `source_note`：**收藏時由收藏者自己填一行字**（選填），之後可隨時於資料庫編輯。

**備註那一行就是來源標記，不另做「來自分享」徽章**：一個泛用徽章的資訊量遠低於「DM 核准的版本」，兩者並存只是把同一件事說兩次。備註留空時，該行以灰字顯示「來自分享」作為空狀態——既保住可辨識性，也順便提示可以補一句。

墊底的理由是備註為選填：若完全不標記，跳過備註的收藏項會與自建的無異，而「來源已更新」的提示與「更新副本」按鈕會突然出現在使用者以為是自己寫的東西上。

**否決回傳作者資訊**：那要放寬 RPC 的隱私約束，並衍生「作者要用什麼名字露出」的問題（帳號 email 顯然不行）。而收藏者自填的備註完全不涉及作者資料，且更有用——「DM 核准的版本」是作者名字給不了的資訊。

**「更新副本」必須保留備註**：更新的語意是刪除＋重收（D6），但 `source_note` 是收藏者的資料而非來源的，重收時 SHALL 帶過去。否則使用者每次跟進來源都要重打一次備註。

### D8：統一檢視骨架 ＋ 型別內容區塊，以註冊表串接

檢視頁骨架（型別標示、名稱、最後更新時間、行動區、免責說明）對所有型別相同，內容區塊依 `kind` 分派。

以**型別註冊表**集中定義每個 kind 的來源表、Zod schema、內容區塊元件、收藏寫入函式。新增型別是在註冊表加一筆，而不是在檢視頁、收藏流程、分享入口三處各加一個 `if`。

### D9：「我的資料庫」為單一頁面，型別為其中的區塊

新增 `/library`：所有 homebrew 型別分區塊列於同一頁，各項標示自建或收藏而來，新增與編輯就地以 `EditorSheet` 開啟（編輯器本來就是 sheet，不需要獨立頁面）。

**否決「索引頁 ＋ 各型別子頁」的兩層結構**：一個玩家的自創內容通常是個位數，為了三個背景兩個子職多跳一層純粹是稅。單頁也讓「我收藏了什麼」一眼看完，而那正是收藏模型需要的落點。

**自建與收藏來的混在同一區塊**，不分成「我建立的」與「我收藏的」兩區。選子職時使用者不在乎那是誰寫的，分兩區只會讓找一個東西要看兩個地方；而「我收了哪些別人的」這個需求由 `source_note`（D7）那一行滿足，不需要靠版面切分，也不需要額外的徽章。

`/custom-backgrounds` 與 `/custom-subclasses` 轉為導向 `/library`，既有連結不失效；系統設定頁的兩條連結收斂為一條。

**型別成長時的退路**：若日後型別多到單頁過長，區塊改為可摺疊即可，不需要改變資訊架構。

### D10：首版型別範圍為背景與子職

兩者的來源表都已存在、都是「顯示文字」型的 homebrew，不需要任何機制建模。種族（`custom-species`）解凍後加入註冊表即可，不需再動本 change 的任何流程。

職業、武器、法術的排除理由見 proposal Non-Goals。

### D11：外來內容一律以純文字呈現

分享內容視為**不可信輸入**：以與使用者手動建立完全相同的 Zod schema 驗證（欄位白名單、長度上限、列舉值），驗證失敗則拒絕收藏並說明原因。

驗證 SHALL NOT 比手動建立更嚴格——凡手動建立時允許自由填寫的欄位，收藏時同樣允許；否則會出現「自己建得起來卻分享不出去」的荒謬狀態。

文字 SHALL NOT 進入 5etools 標記渲染路徑：外來字串不得觸發內容庫交叉引用。`{@spell ...}` 形式的字串原樣顯示。

### D12：無公開列舉介面（規格層約束）

不提供任何列舉、瀏覽或搜尋他人分享內容的介面；資料庫層不開放支援列舉的公開查詢路徑（依 `owner_id`、`created_at`、`kind` 的無 token 查詢一律不存在）。

這既是隱私設計，也是著作權護欄——App 不成為內容散布平台。未來若要提供公開索引，SHALL 經明確的規格變更，SHALL NOT 以實作方便為由繞過。

## Risks / Trade-offs

- **主鍵變更影響既有資料** → 8 筆與 0 筆，且僅加欄位進主鍵、不改 id 值；`user_backgrounds` 無外來鍵指入，風險低
- **作者在檢視者按下收藏的瞬間修改內容** → 收到的是按下當下的版本。這是活資料的固有性質，且窗口以秒計；不做交易保護
- **`updated_at > created_at` 的本地編輯偵測失準** → D6 已載明；需維持「只在實際儲存時 upsert」
- **作者刪除來源導致連結失效** → `deleted` 狀態；已收藏者不受影響（D2）
- **新增 kind 時漏接某條流程** → D8 的註冊表；漏掉會是編譯期錯誤而非執行期靜默
- **收藏同一 token 兩次產生重複資料列** → 見 Open Questions
- **規則版本標示與檢查全數依賴凍結中的 `dual-rules-version`** → 首版完全不顯示版本；顯示推定值會在 5e 上線後讓既有分享全部標錯（D4）
- **著作權**：無索引、無搜尋、token 不可枚舉，內容僅點對點傳遞

## Migration Plan

1. `user_backgrounds` / `user_subclasses` 主鍵改為 `(user_id, id)`（D3）
2. 兩表新增 `source_token`、`source_updated_at`、`source_note`（皆 nullable，無需回填）
3. `homebrew_shares` 表、RLS、`get_shared_homebrew` RPC（不動既有表）
4. 型別註冊表與資料層（發布、撤銷、依 token 取回、收藏）
5. 統一檢視頁與背景／子職的內容區塊
6. `/library` 我的資料庫（既有兩頁轉為導向）
7. 分享入口、來源標記、「更新副本」
8. 「直接套用到這個角色」（見 Open Questions，可能延後）

回退：移除 UI 入口即可；新表與新欄位留著不影響任何既有功能。主鍵變更不可逆，但也無需回退——它嚴格比原狀態安全。

## Open Questions

- **收藏同一 token 兩次要擋還是允許？** 擋住較乾淨，但使用者可能刻意要兩份再各自改。傾向允許但提示「你已收藏過這份」
- ~~**檢視頁是否顯示作者名稱？**~~ **已定：不顯示**（D7）。底層需求是「三個月後認得出這是誰給的」，而那由收藏者自填的 `source_note` 解決，不必放寬 RPC 的隱私約束，也不必回答「作者要用什麼名字露出」
- **「直接套用到這個角色」首版是否納入？** 只做收藏就已經打通「設計 → 審核 → 採用」的完整流程（收藏後在建角／升級流程自然可選）。直接套用省一次跳轉，但要在檢視頁引入角色上下文與各型別的規則判定，複雜度不低
