## Context

動機見 proposal。以下為實查所得的現況：

| 自訂內容 | 角色卡上的痕跡 | 可判定？ |
|---|---|---|
| 自訂背景 | 僅 `background: z.string()` 的名稱 | **否**——與 SRD 背景無異 |
| 自訂子職 | `customSubclass` 整份快照（`character.ts:187`） | 是，但**無任何畫面讀取** |
| 自訂子職特性 | `source: '子職：X・自訂'`（`level-up-view.tsx:154`） | **否**——字串後綴慣例 |
| 自訂起源專長 | 無 | **否** |

`customSubclass` 快照的存在證明資料層已經備妥，缺的是呈現與可判定的旗標。

既有的相關原則：
- 選用時**快照**進角色卡，後續一律自快照取用，不回查來源表（`custom-subclass` design D5）
- 來源以**旗標**而非名稱判斷（`custom-subclass` design D4、`custom-origin-feat`）——使用者自訂一個與 SRD 同名的內容時，那是他的
- UI 標示用「文字＋數值」而非裸符號

## Goals / Non-Goals

**Goals:**
- DM 看角色卡（自己的或分享連結）時能一眼分辨哪些是自創內容
- 標示為可判定的資料，不依賴字串比對
- 角色卡頁與分享頁的呈現一致

**Non-Goals:**
- 審核狀態機、平衡驗證、回連來源、自訂種族（見 proposal）

## Decisions

### D1：旗標記錄「是不是自創」，不記錄來源 id

新增 `backgroundIsCustom: boolean` 與 `CharacterFeature.isCustom: boolean`。**不新增 `customBackgroundId` 之類的欄位。**

否決記 id：角色卡上的自創內容一律是快照，而 id 唯一的用途就是回查來源——那正是快照哲學明確禁止的事（來源可能已被刪除）。留一個 id 在那裡只會誘使日後有人寫出回查的程式碼。旗標承載的是唯一真正需要的事實。

子職是唯一的例外，但它的例外已經成立：`customSubclass` 存的是**整份快照**而非 id，後續等級自快照取用。旗標對子職而言是冗餘的——`customSubclass !== null` 就是旗標。

### D2：`CharacterFeature` 的 `source` 回歸單純描述

目前自訂子職特性的來源字串是 `子職：${name}・自訂`。改為 `source: 子職：${name}` ＋ `isCustom: true`。

否決保留後綴：字串後綴讓「是否自訂」這個判斷散布在每個要顯示它的地方，且任何措辭調整都會讓標示靜默消失。既然要為呈現加旗標，就該讓字串停止承載語意。

**既有角色的相容**：已有的特性條目其 `isCustom` 預設為 `false`，而其 `source` 仍帶 `・自訂` 後綴——**畫面上會顯示為「子職：烈焰學派・自訂」但沒有旗標標示**。處置見 D3。

### D3：既有角色的回填只做特性，不做背景

**特性可回填**：`source` 以 `・自訂` 結尾的條目，其 `isCustom` 設為 `true` 並移除後綴。這是精確的——那個後綴只有一處程式碼會產生。

**背景不回填**：無法可靠判定。唯一的線索是「角色的 `background` 名稱是否出現在該使用者的 `user_backgrounds` 中」，但那會在使用者自訂了一個與 SRD 同名的背景時誤判，也會在使用者刪掉那個自訂背景後失效。

接受這個限制：**既有角色的自訂背景不會被標示**，新建與其後編輯過背景的角色才有。這比猜錯好——一個沒標示的自訂背景只是少了資訊，一個標錯的會讓 DM 誤判。此限制 SHALL 於實作時記錄於程式碼註解，避免日後被當成 bug 修成猜測式回填。

> 回填涉及動使用者資料表，一律帶 `user_id` 條件執行。

### D4：標示的呈現位置與措辭

| 位置 | 呈現 |
|---|---|
| 概覽的背景欄 | 名稱後加「自訂」標籤 |
| 概覽的子職 | 同上 |
| 特性列表 | 條目的來源行加「自訂」標籤 |

措辭一律為「自訂」二字，不用圖示、色塊或裸符號——與既有的「chip 用文字＋數值」慣例一致。新手看到「自訂」知道那是什麼；看到一個小星號不知道。

### D5：分享頁與角色卡頁共用同一呈現

`/v/[token]` 的角色卡呈現與 `/main/character` 使用同一組元件，因此標示自動一致。**這是本 change 的主要目的地**——DM 看的是分享連結，不是玩家的畫面。

實作時 SHALL 驗證分享頁確實顯示標示，而非僅在登入的角色卡頁測過就算數。

## Risks / Trade-offs

- **既有角色的自訂背景無標示** → D3 已接受並說明理由；需以程式碼註解固定該決定
- **旗標與 `customSubclass` 冗餘** → 子職不加旗標，以 `customSubclass !== null` 判定（D1）
- **回填動到使用者資料** → 只改特性條目、且僅針對精確的後綴比對；帶 `user_id` 條件
- **標示被誤解為「未經核准」** → 措辭為「自訂」而非「未驗證」「待審核」；本 change 明確不做審核狀態

## Migration Plan

1. `character.ts` 新增 `backgroundIsCustom` 與 `CharacterFeature.isCustom`（皆 `.default(false)`，既有文件無需回填即可解析）
2. 建角與升級的寫入端設定旗標；移除 `・自訂` 後綴
3. 角色卡頁與特性列表的呈現
4. 分享頁驗證
5. 既有特性條目的一次性回填（D3）

回退：旗標為純標示，移除呈現即可；欄位留著不影響任何推導。

## Open Questions

- 自訂**起源專長**（來自自訂背景）目前在角色卡上如何呈現？若它已混入 `features`，是否也該帶旗標——需先確認 Next.js 端是否已移植該功能
- 概覽的背景欄與特性列表之外，**角色清單卡片**是否也需要標示？傾向不需要——那層只顯示名稱與等級，加標示會讓卡片變吵
